## ГЛАВНЫЙ РЕЗУЛЬТАТ

Создай **реально работающую сцену Water Lab**, где пользователь может наклонять ёмкости и наблюдать, как вода с задержкой переливается из одного отсека в другой и обратно. Клапан перекрывает поток. Насос гонит воду в обратном направлении и поднимает её против уклона. В воде плавают/тонут **реальные PhysicsBall / RigidBody3D** из P1; поток оказывает силу, сопротивление замедляет тела. Графика воды всегда следует данным симуляции.

НЕ ограничивайся поиском, техдокументом, визуальным шейдером или фиктивным «движением воды» через Tween. Нужны код, сцена, воспроизводимые тесты.

## 2. МОДЕЛЬ ВОДЫ

Разделить 3 логических слоя: Hydraulics / Forces / Visual.

Для Android GL Compatibility: использовать лёгкую **сетевую модель резервуаров** или малую shallow-water сетку. Физика не зависит от GPU; состояния жидкости существуют без рендера. Поток между связанными ёмкостями вызывается перепадом гидравлического напора, а направления относительно мира меняются от наклона платформы. Учитывай высоту отверстий, вместимость, ограничение по дебиту, открытие клапана и насосное давление.

В начале шага известны все объёмы; обновление потока не должно создавать/удалять объём. Схема: расчёт flux для каждой связи -> ограничение доступной жидкостью/ёмкостью -> согласованное применение к обоим концам, чтобы результат не зависел от порядка обхода. Никаких отрицательных объёмов и воды поверх максимального уровня без явного overflow-канала.

Наклон ёмкости: вода в статическом приближении сохраняет world-horizontal свободную поверхность относительно мировой g, а жидкости нужна сглаженная кратковременная реакция/инерция (sloshing). Контейнер может наклоняться, но вода НЕ просто поворачивается вместе с его Mesh. Для внутренних препятствий и длинных желобов использовать low-resolution ячейки с локальной высотой и потоками.

Реверс: изменить уклон или включить насос — жидкость действительно движется в другую сторону; когда насос выключен, он не должен бесплатно тащить воду вверх против гравитации.

Оставить расширяемые настройки плотности воды, вязкости, гравитации, трения стенок и температуры для будущего Water↔Ice/Steam и Lava P5. P2 не обязан делать кипение/лаву, но API должен быть пригоден для следующего этапа.

## 3. СИЛЫ ДЛЯ ШАРОВ P1

Шары — только существующие PhysicsBall на основе RigidBody3D.

При попадании в WaterVolume: вычислять погружённую долю объёма шара, world-space поверхность, плотность воды и текущий вектор течения. Прикладывать силу Архимеда и сопротивление к относительной скорости шар/вода в каждом физическом tick. Вывести из расчёта детерминированное поведение: лёгкий/пустотелый или деревянный шар плавает, тяжёлый стальной тонет; мокрая поверхность снижает/меняет контактное трение только при наличии воды.

**Особая проверка:** в P1 у BallMaterialProfile заданы И mass, И density, а radius PhysicsBall конфигурируется отдельно; эти числа могут быть не согласованы с геометрическим объёмом. Не делай физически бессмысленную плавучесть (например, тяжёлый шар внезапно плавает из-за слишком маленькой массы). Выбери и задокументируй консистентное правило расчёта effective density/displaced volume, откалибруй данные и зафиксируй тестами.

Полное/частичное погружение должно вести себя плавно, без смены трансформа и без рывков на границе. Учти сон физического тела и устойчивость при переходе сухо/вода. Никакой телепортации или зафиксированной анимации на водной поверхности.

## 4. ВИЗУАЛ И УПРАВЛЕНИЕ WATER LAB

- Изометрическая 3D камера, явная разметка Reservoir A/B, Valve, Pump, Tilt, направление воды, количество (литры или относительные объёмы).
- Вода видна и имеет меняющийся уровень, волны/пена только как дополнительные эффекты, без тяжёлых GPU compute зависимостей. Если transparency проблемна в Compatibility, реализуй надёжный простой mobile-friendly вариант.
- На Android кнопки/жесты наклона, клапан, насос и реверс; на Windows клавиатура/мышь.
- Игрок видит, какой из двух шаров всплывает/тонет, и как поток переносит шар; UI не перекрывает рабочую конструкцию. На телефоне не полагаться только на гироскоп.
- Кнопка Reset восстанавливает точные начальные объёмы и положения шаров; время и обновление не должны продолжаться при паузе.

## 5. СТРОГИЕ HEADLESS-ТЕСТЫ

1. Водная сеть при закрытом клапане не перетекает, при открытом идёт вниз.
2. Смена уклона даёт поток в обратную сторону при существующем пути.
3. Насос переносит определённый объём вверх; при выключенном насосе вода не движется вверх сама.
4. За 1000+ physics ticks абсолютная ошибка сохранения общего объёма меньше разумного установленного допуска; ни один резервуар не уходит в минус и не превышает ёмкость.
5. Из ограниченной заполненной чаши часть воды переливается через слив в заданный приёмник, масса не исчезает без обозначенной сливной ёмкости.
6. Деревянный/пустотелый шар имеет устойчивую плавучесть; стальной тонет, с настоящим движением RigidBody3D и collision.
7. Скорость одного и того же шара в воде заметно отличается от его скорости в воздухе; течение может сместить его горизонтально.
8. Визуальный уровень отражает рассчитанную высоту; Reset восстанавливает начальное состояние; отсутствие ошибки парсинга/import.
9. Регрессии проходят: P1 physics_lab_test.gd, smoke_test.gd, level_02_smoke_test.gd, mobile_controls_test.gd.
10. Запусти scene headless минимум 180 кадров; собери Android Debug APK GitHub Actions, проверь package ID, versionCode auto increment и артефакт. Постоянный стабильный ключ не генерируй; без секретов можно собрать только debug, который не обновляет произвольную старую установку.

**Не засчитывать тест, который проверяет лишь изменение чисел без реальной физики RigidBody3D.**
